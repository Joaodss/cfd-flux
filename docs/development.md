# Development environment

## Requirements

| Tool | Version | Used for |
|------|---------|----------|
| Rust (rustup) | ≥ 1.87 (wgpu 30; tested with 1.99) | `crates/` workspace |
| Node.js | ≥ 22 (tested with 24) | `apps/web` |
| CUDA Toolkit | 13.x (tested with 13.4), only to *run* the CUDA backend | `cfd-cuda` (NVRTC); building needs nothing |

**Author's machine (verified 2026-10-09; driver updated 2026-10-12):** RTX 4060 8 GB (`sm_89`), driver 617.42 (CUDA 13.4; was 610.62 = CUDA 13.3),
CUDA Toolkit 13.4, VS Build Tools 2022 (MSVC 14.4x), Rust 1.90 `stable-x86_64-pc-windows-msvc`, Node 24.
Native `cargo build/test` and a CUDA test kernel (`nvcc -arch=sm_89`) both work.

### CUDA on Windows — notes

- `nvcc` needs the MSVC environment loaded: use the "x64 Native Tools Command Prompt for VS 2022" or
  call `vcvars64.bat` first. Outside that environment it fails with `nvcc fatal: Host compiler targets unsupported OS`.
- In CUDA 13 the DLLs (including `nvrtc64_130_0.dll` and `nvrtc-builtins64_134.dll`) live in
  `CUDA\v13.4\bin\x64`. `cfd-cuda` finds them on the PATH or, failing that, through `CUDA_PATH`.
- **Driver older than the toolkit** (610.62 = 13.3 vs 13.4 until 2026-10-12): binaries compiled for `sm_89` (SASS/cubin) work; PTX
  generated by NVRTC 13.4 may be rejected by the driver's JIT. `cfd-cuda` therefore compiles straight to a
  cubin and only falls back to PTX when the driver is at least as new as NVRTC (ADR-021).
- Profiling: Nsight Systems (`nsys profile --trace=cuda …`) works as a normal user; Nsight Compute and
  hardware counters need "Allow access to the GPU performance counters to all users" in the NVIDIA Control
  Panel (Developer → Manage GPU Performance Counters), otherwise `ncu` stops with `ERR_NVGPUCTRPERM`.

### Windows: Rust toolchain

Recommended (and in use): the **MSVC** toolchain (`stable-x86_64-pc-windows-msvc`) with **Visual Studio Build Tools 2022**
and the "Desktop development with C++" workload. It is Rust's default toolchain on Windows, and CUDA on
Windows needs the MSVC C++ compiler as well.

```powershell
winget install Microsoft.VisualStudio.2022.BuildTools --override "--quiet --wait --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"
rustup default stable-x86_64-pc-windows-msvc
```

> **Resolved issue (2026-10-09)** by switching to MSVC — kept for reference: with the `windows-gnu` toolchain and the old
> MinGW.org in `C:\MinGW\bin` on the PATH, `cargo build` fails in `windows-sys` ("Dlltool could not create import
> library") because there is no x86-64 assembler. `cargo check`/`clippy` still work; to build/test use the MSVC
> toolchain (above) or WSL.

## Commands

```bash
# Rust
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace

# Scene format: after changing crates/cfd-core/src/scene.rs or examples.rs
cargo run -p cfd-cli -- schema schema/scene.schema.json
cargo run -p cfd-cli -- example --all scenes
cd apps/web && npm run gen:types

# Preset fluids and solids (cfd-core/src/library.rs) for the web editor; a test checks it is up to date
cargo run -p cfd-cli -- library apps/web/src/generated/library.json

# Check scene files
cargo run -p cfd-cli -- validate scenes/*.json

# Run a scene headless (frames, PNGs, CSV series, meta.json); re-render PNGs with other ranges.
# --backend auto (default) uses CUDA, else a hardware GPU through wgpu, else the CPU.
cargo run --release -p cfd-cli -- run scenes/cylinder-re100.json --out out/cyl --end-time 12 --output-interval 0.05
cargo run --release -p cfd-cli -- render out/cyl --range vorticity=-50:50

# Performance (results go to docs/benchmarks.md) and physics validation (docs/08-validation-guide.md)
cargo run --release -p cfd-cli -- bench --backend cpu --threads 8
cargo run --release -p cfd-cli -- bench --backend wgpu --sizes 256,512,1024,2048,4000
cargo run --release -p cfd-cli -- bench --backend cuda --sizes 256,512,1024,2048,4000
cargo run --release -p cfd-cli -- bench --backends cuda,wgpu --sizes 256,512,1024,2048,4000 --repeat 5  # interleaved, one column per engine
cargo run --release -p cfd-cli -- verify --quick --backend cpu   # CI subset, ~20 s
cargo run --release -p cfd-cli -- verify --full --backend cpu    # writes validation/report/ (commit it)
cargo run --release -p cfd-cli -- verify --full --backend wgpu   # writes validation/report-wgpu/ (commit it)
cargo run --release -p cfd-cli -- verify --full --backend cuda   # writes validation/report-cuda/ (commit it)
cargo run --release -p cfd-cli -- verify --cases cavity --no-report

# Engine comparison (ADR-023): the same scene on several backends, against the first one.
# Default: every available backend (cpu, cuda, wgpu); exit code 1 outside the tolerance.
# Its end-to-end tests (crates/cfd-cli/tests/compare.rs) skip GPU backends like the parity tests
# (CFD_REQUIRE_GPU / CFD_REQUIRE_CUDA make them fail instead).
cargo run --release -p cfd-cli -- compare scenes/channel.json --out out/cmp --steps 2000
cargo run --release -p cfd-cli -- compare scenes/channel.json --out out/cmp --force --backends cpu,cuda --tolerance 0  # must be bit-identical
cargo run --release -p cfd-cli -- compare scenes/cylinder-re100.json --out out/cmp-cyl --end-time 12 --statistics --stats-from 6 --ref-length 0.1 --ref-velocity 1
cargo run --release -p cfd-cli -- compare --validation   # writes validation/compare/ (commit it), ~1 min

# Server (Phase 3): API on http://127.0.0.1:7878, data (SQLite + results/) in ./data
cargo run --release -p cfd-server
cargo run --release -p cfd-server -- --listen 127.0.0.1:8080 --data /tmp/lf --cpu-jobs 2
# Its test client: submit a scene, follow the stream, optionally cancel (prints the latency)
cargo run --release -p cfd-cli -- submit scenes/cylinder-re100.json --backend cuda --cancel-after 3
cargo run --release -p cfd-cli -- submit scenes/channel.json --end-time 2 --fields velocity --max-size 256
curl -s http://127.0.0.1:7878/api/capabilities

# Web (in apps/web)
npm install
npm run dev          # development server
npm test             # Vitest (checks scenes/ against the JSON Schema)
npm run typecheck && npm run lint && npm run format:check && npm run build
```

## Server

- `cfd-server` opens every engine once at start-up (CUDA, a hardware wgpu adapter, the CPU) and logs what it
  found; `--allow-software` lets jobs that ask for wgpu use WARP/lavapipe. `RUST_LOG=cfd_server=debug,tower_http=debug`
  shows every request. No authentication: keep the default loopback address unless the network is trusted.
- Data: `<data>/cfd-flux.db` (SQLite: jobs and saved scenes) and `<data>/results/<job id>/` (the
  [03 §6.2](03-data-model.md#62-storage) layout; `cfd-cli render <dir>` makes PNGs from it). Jobs active when the
  server stops become `failed/interrupted`.
- The API and the WebSocket messages are in [03 §7](03-data-model.md#7-api). Quick checks with `curl`:
  `POST /api/scenes/validate` with a scene file as the body; `POST /api/simulations` with `{"scene": …}`.
- Tests: `crates/cfd-server/tests/` start the server in-process on an ephemeral port with an in-memory database
  (`api.rs`: capabilities, validation, limits, CORS; `jobs.rs`: lifecycle, cancel, pause, queueing, purge,
  restart; `stream.rs`: WebSocket, backpressure, and the acceptance scenario on every available engine, skipped
  like the parity tests unless `CFD_REQUIRE_GPU`/`CFD_REQUIRE_CUDA` is set). `crates/cfd-cli/tests/submit.rs`
  runs `cfd-cli submit` against an in-process server.

## GPU (wgpu) backend

- `cargo test --workspace` runs the CPU ↔ wgpu parity tests (`crates/cfd-gpu/tests/parity.rs`) on the best adapter
  it finds, software ones included; without any adapter they print `skipping` and pass. Set `CFD_REQUIRE_GPU=1` to
  make them fail instead (CI does).
- Software adapters: **WARP** (DX12) ships with Windows; on Linux install Mesa's **lavapipe**
  (`sudo apt-get install mesa-vulkan-drivers`). `--backend auto` never picks them (slower than the CPU backend);
  `--backend wgpu --allow-software` does.
- Choosing an adapter: `CFD_WGPU_ADAPTER=<part of the name>` (e.g. `"basic render"` for WARP), and wgpu's own
  `WGPU_BACKEND=vulkan|dx12`. The chosen adapter is printed by `run`/`bench`/`verify` and stored in `meta.json`
  and the reports.
- The shaders are in `crates/cfd-gpu/shaders/`; constants shared with the CPU are generated into a WGSL prelude
  (`cfd_lbm::abi`). naga validates every shader in `cargo test`, with or without a GPU.

## CUDA backend

- `cfd-cli` is built with the `cuda` feature by default (`--no-default-features` leaves it out). `cudarc` opens
  the driver and NVRTC at runtime, so building needs no toolkit; running needs an NVIDIA driver supporting
  CUDA ≥ 13.0 and the CUDA 13 NVRTC (from the toolkit). Errors say which of them is missing.
- `cargo test --workspace` runs the CPU ↔ CUDA parity tests (`crates/cfd-cuda/tests/parity.rs`, the shared cases
  of `cfd_verify::parity`) when a device is found and prints `skipping` otherwise; `CFD_REQUIRE_CUDA=1` makes them
  fail instead. `CFD_REQUIRE_NVRTC=1` requires only NVRTC: the kernels compile and their layout `static_assert`s
  are checked without a GPU (CI job `cuda-kernels`).
- `CFD_CUDA_DEVICE=<ordinal>` selects the device. `--backend auto` prefers CUDA, then a hardware wgpu adapter,
  then the CPU, and prints why each engine was skipped.
- The kernels are in `crates/cfd-cuda/kernels/` and compiled by NVRTC on first use (≈ 0.3 s per process) with
  `--fmad=false`, which makes them bit-identical to the CPU backend; `cfd-cli … --fmad` compiles them with fused
  multiply-adds. All `unsafe` code is in `crates/cfd-cuda/src/raw.rs`.
- Memory checks: `compute-sanitizer --tool memcheck <test binary>` (in `CUDA\v13.4\bin`) on the parity tests.

## Conventions

- **Everything in English** — code, identifiers, comments, docs, UI text and commit messages ([ADR-013](07-decisions-and-questions.md)).
- `schema/scene.schema.json`, `scenes/*.json` and `apps/web/src/generated/` are **generated** — do not edit them by hand.
  The Rust tests and the web CI fail if they are out of date.
- Work on branches and merge into `master` through pull requests; CI must be green.
