# 05 — Implementation plan

## 0. Strategy

1. **Solver first, no web.** A validated, fast solver is the core; the UI is useless without it. The CLI allows iterating without a server or browser.
2. **CPU as the reference, GPU for production.** The CPU backend is simple and correct; the GPU backends are compared against it in every test.
3. **Early vertical slices.** As soon as there is a minimal CPU solver, connect it to an API and a rough canvas (Phases 3/4 can start in parallel with Phase 2).
4. **Stable contracts:** the `Scene` format and the frame protocol are defined in Phase 0 and evolve through versions.

Indicative effort per task: **S** (≤ 1 day), **M** (2–4 days), **L** (1–2 weeks). For one person working part-time, scale according to availability.

```
Phase 0 Foundations ─▶ Phase 1 CPU solver ─┬─▶ Phase 2 GPU ────────────────┐
                                           ├─▶ Phase 3 Server ─────────────┼─▶ MVP ─▶ Phases 6–10
                                           └─▶ Phase 4 Editor ─▶ Phase 5 Vis┘
                                           (MVP = Phases 0–5 + 6a: liquids with a free surface)
```

### Learning prototypes (Rust + GPU) — before or alongside Phase 1

Goal: get fluent in Rust and GPU programming with throwaway code before writing the "real" code. They live in `sandbox/` (outside the main workspace).

- [ ] S — Rustlings or chapters 1–10 of *The Rust Book*; focus on ownership/borrowing, `Result`/`?`, traits (≈ C# interfaces), enums with data (≈ discriminated unions).
- [ ] M — Minimal D2Q9 LBM in a single `main.rs` (128² cavity, writes a PNG with the `image` crate). First sequential, then with `rayon` (`par_chunks_mut`).
- [ ] S — "Hello compute" in `wgpu`: add two vectors in a WGSL compute shader and read the result back.
- [ ] S — "Hello compute" in `cudarc`: the same with a `.cu` kernel compiled by NVRTC.
- [ ] S — Port the minimal LBM kernel to wgpu **or** CUDA and compare MLUPS with the CPU version.

Notes for C# developers:
- Instead of object graphs with cross references (which fight the borrow checker), use **arrays + indices** — exactly what a solver needs anyway.
- Errors: `thiserror` in libraries, `anyhow` in applications (CLI/server).
- `async` in Rust (tokio) ≈ C# `async/await`, but the solver runs on a normal thread, outside the async runtime.
- Tools: VS Code + rust-analyzer (or RustRover), `cargo clippy`, `cargo nextest`, `criterion` for benchmarks, Nsight Compute to profile CUDA kernels, RenderDoc/Nsight Graphics for wgpu.

**Acceptance:** `cargo test` and `npm test` green in CI; an example scene is validated by the schema on both sides.

## Phase 1 — CPU solver core (LBM)

**Goal:** a correct, validated 2D LBM, runnable from the CLI.

- [x] M — `cfd-core`: `Domain`, per-cell flags, `Scene → Domain` conversion, units module (physical ↔ lattice) with stability checks and warnings. *(2026-10-10)*
- [x] M — `cfd-lbm`: D2Q9 BGK, fused stream-collide kernel (pull), ping-pong, parallelised by rows with `rayon`. *(SoA, shifted populations; ≈ 120 MLUPS on 16 threads)*
- [x] M — Boundary conditions: bounce-back, moving wall, velocity inlet, pressure and zero-gradient outlets, periodic. *(link-wise: velocity bounce-back instead of Zou-He, see ADR-014)*
- [x] S — Guo forcing (body force and Boussinesq buoyancy; hydrostatic gravity goes into the output pressure, ADR-016).
- [x] M — TRT operator (default), keeping BGK as an option.
- [x] M — Thermal D2Q5 + Boussinesq; fixed/adiabatic/flux thermal BCs.
- [x] S — Diagnostics: mass, energy, maximum velocity, NaN detection.
- [x] M — `cfd-cli run`: reads a scene, runs it, writes PNGs (colour map) and binary frames; `cfd-cli bench` reports MLUPS. *(2026-10-10; also `render`, probe/force/diagnostic CSVs, `meta.json`, clean abort on NaN; results in [benchmarks.md](benchmarks.md))*
- [x] L — Automated validation suite (`cfd-cli verify`, methodology in [08](08-validation-guide.md)), including convergence-order tests: Poiseuille, Couette, Taylor-Green, cavity (Ghia), cylinder (Schäfer-Turek), heated cavity (de Vahl Davis). Produces a report with errors and plots. *(2026-10-10; crate `cfd-verify`, ADR-018; report in [`validation/report/`](../validation/report/README.md); `--quick` runs in CI)*
- [x] S — Forces on solids (momentum exchange) for C_D/C_L; probes. *(time series written to CSV by `cfd-cli run`; forces are gauge)*

**Acceptance:** all applicable cases from [04 §7](04-numerical-methods.md#7-validation) within tolerance; ≥ 50 MLUPS on 8 cores; von Kármán street visible for the Re 100 cylinder. **Met (2026-10-10):** 12/12 validation cases pass (`verify --full`); 65–137 MLUPS on 8 threads; vortex street in `cfd-cli run scenes/cylinder-re100.json` and in the report. Still to automate: the Rayleigh-Bénard onset case of 04 §7 (first task of Phase 2, on the CPU backend).

## Phase 2 — GPU backends (wgpu + CUDA)

**Goal:** the same solver on the GPU, 10–50× faster, with automatic fallback, in **two comparable engines**: wgpu/WGSL (portable) and CUDA (NVIDIA). See [ADR-002](07-decisions-and-questions.md).

Suggested order: wgpu first (2a), CUDA right after (2b), comparison at the end (2c). The kernels share the same memory layout (SoA, same indexing, same flags) so the comparison is fair and tests are reusable.

- [ ] S — *(carried over from Phase 1)* Rayleigh-Bénard onset case in `cfd-verify` (Ra_c ≈ 1708, 04 §7), validated on the CPU backend before the GPU backends reuse the suite.

### 2a — wgpu / WGSL

- [ ] M — `cfd-gpu`: adapter discovery, device selection, limits (`max_storage_buffer_binding_size`), CPU fallback when there is no GPU/memory.
- [ ] M — SoA buffers for `f_i`, flags, per-element parameters (uniform/storage); D2Q9 TRT stream-collide WGSL kernel.
- [ ] M — BCs in WGSL (element table indexed by flags, avoiding unnecessary divergent branches).
- [ ] M — Thermal D2Q5 in WGSL.
- [ ] M — GPU reductions (diagnostics, forces) and a sampling/f16 conversion kernel before copying to the CPU.
- [ ] S — Asynchronous readback with double-buffered staging (the simulation keeps running while a frame is copied).
- [ ] M — GPU vs CPU parity tests (tolerance in [04 §7](04-numerical-methods.md#7-validation)); run when an adapter exists (including software ones such as lavapipe/WARP in CI).
- [ ] S — Benchmarks at several resolutions; recorded in `docs/benchmarks.md`.
- [ ] M — (Optional) AA pattern / Esoteric Pull to halve memory.

### 2b — CUDA (`crates/cfd-cuda`, Cargo feature `cuda`)

- [ ] S — `cfd-cuda` crate with `cudarc`; conditional compilation (`--features cuda`) so the workspace builds without the CUDA Toolkit; device and *compute capability* detection.
- [ ] M — CUDA C kernels (`kernels/*.cu`) compiled at runtime by NVRTC — preferably straight to `sm_89` cubin (see [development.md](development.md)): D2Q9 TRT stream-collide, BCs, D2Q5 thermal — a direct translation of the WGSL kernels, same indexing.
- [ ] M — Reductions (diagnostics, forces) with warp shuffles; f16 sampling; asynchronous copies with streams and pinned memory.
- [ ] S — Implement the `Solver` trait (`CudaLbm`, ADR-017) → `BackendKind::Cuda`; `backend: "auto"` prefers CUDA > wgpu > CPU (configurable).
- [ ] M — CUDA vs CPU parity tests (same tolerance); only run with `--features cuda` and an NVIDIA GPU (self-hosted CI job or manually).

### 2c — Engine comparison

- [ ] M — `cfd-cli compare scene.json --backends cpu,wgpu,cuda --steps N`: runs the same scene on each backend and reports per-field differences (max absolute, relative L2, difference map as PNG), diagnostics (mass, energy) and MLUPS.
- [ ] S — `cfd-cli bench --backends wgpu,cuda`: MLUPS table per resolution (256² → 4096²), f32 and (later) f16; results in `docs/benchmarks.md`.
- [ ] S — In the API/UI (Phases 3–5): the chosen backend shows up in the job metadata; the same scenario can be launched on two backends and the differences viewed side by side (reusing the comparison UI).

**Acceptance:** CPU↔wgpu↔CUDA parity within tolerance; ≥ 1,000 MLUPS at 1024² on both engines (NFR-01 targets ≥ 2,000 on the RTX 4060); `cfd-cli compare` produces a report for the validation cases; CUDA → wgpu → CPU fallback tested.

## Phase 3 — Server and jobs

**Goal:** simulation requests over HTTP with streamed results.

- [ ] M — `cfd-server` with axum: routes from [03 §7](03-data-model.md#7-api-draft), body size limits, CORS, tracing.
- [ ] M — Server-side scene validation (schema + consistency rules + stability) with localisable messages (stable issue codes).
- [ ] M — Job manager: in-memory queue, states (`queued/running/paused/completed/failed/cancelled`), per-device semaphore, cooperative cancellation.
- [ ] M — Worker loop on a dedicated thread (the solver never blocks the tokio runtime); channel for frames. The loop processes **commands** (`Step`, `Pause`, `Resume`, `Cancel`, `PatchCells`, `SetParam`) between batches of steps — the foundation of interactive mode ([ADR-011](07-decisions-and-questions.md)).
- [ ] M — WebSocket: progress (JSON) + frames (binary); backpressure (if the client is slow, drop intermediate *streaming* frames but keep all of them on disk).
- [ ] M — `ResultStore` on disk; SQLite for job and scene metadata.
- [ ] S — `/api/capabilities` (backends, GPU, limits).
- [ ] S — Integration tests: submit scene → receive N frames → `completed`.

**Acceptance:** a test client (script) submits the cylinder and receives frames in real time; cancelling works in < 1 s.

## Phase 9b — Other states of matter

Goal: **all common phase changes**, including granular materials (e.g. crushed ice melting in a glass). Proposed approach in [ADR-012](07-decisions-and-questions.md).

| Transition | Example | Proposed method |
|------------|---------|-----------------|
| Solid ↔ liquid (continuum) | Block of ice melting, metal solidifying | Enthalpy method + LBM (mushy zone as a porous medium) |
| **Granular ↔ liquid** | **Crushed ice melting** | MPM with temperature and latent heat per particle; melted mass → liquid |
| Liquid ↔ gas | Boiling, evaporation, condensation | Thermal multiphase LBM (pseudo-potential or phase-field with a mass source) |
| Solid ↔ gas *(Phase 9c)* | Sublimation (dry ice), deposition (frost) | Enthalpy + interfacial mass transfer |
| Gas ↔ plasma *(Phase 9c)* | Ionisation | Depends on the plasma work |

- [ ] L — Enthalpy method (melting/solidification) with validation: Stefan problem (analytical solution) and gallium melting in a cavity (Gau & Viskanta 1986).
- [ ] L — **Granular:** 2D MPM (CPU → GPU) with granular rheology (Drucker-Prager), coupled to the fluid; validation: granular column collapse.
- [ ] L — Thermal MPM ↔ fluid coupling with latent heat → crushed ice melting.
- [ ] L — Evaporation/condensation (thermal multiphase LBM); validation: liquid-vapour Stefan problem.

## Phase 9c — Rare transitions (after 9b)

- [ ] M — Sublimation (solid → gas, e.g. dry ice) and deposition (gas → solid, e.g. frost): enthalpy + interfacial mass transfer.
- [ ] M — Other rare cases to evaluate: supercooling (liquid below its melting point), triple point, supercritical fluids, ionisation (gas → plasma).
- [ ] L — **Plasma:** start with 2D resistive MHD (conducting fluid + magnetic field) or a simplified two-fluid model; requires the compressible solver (Phase 7).

## Main risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| LBM instability at high Re | Simulations blow up | TRT/MRT, LES, stability warnings, automatic resolution increase |
| Buffer limits in wgpu/WebGPU (e.g. 128 MB–2 GB per binding) | Large domains fail | Split `f_i` across several buffers; query adapter limits |
| Bandwidth for streaming frames | Sluggish UI | f16 + zstd + downsampling + dropping intermediate frames |
| GPU/CPU numerical differences | Flaky tests | Relative tolerances, tests on aggregated quantities |
| Scope too large | The project never reaches MVP | Strict MVP (Phases 0–5 + 6a); everything else is post-MVP |
